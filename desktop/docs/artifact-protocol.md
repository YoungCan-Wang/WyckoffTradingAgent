# 产物（Artifact）协议

聊天里生成的 K 线、报告怎么变成右侧面板里一个可寻址、可重开、可去重的东西。

## 为什么要这一层

现在这套是靠副作用和文本猜测串起来的：

- K 线在 `tool_start` 就打开 —— 工具还没成功，失败会留一个空面板。
- 报告靠 `looksLikeReport()` 猜（>400 字且有标题或表格），误判漏判都有。
- 产物只存在于命令式 `TabPane` 里，没有会话级列表 —— 关掉页签就找不回来。
- 页签超过 6 个静默淘汰最老的，而对话里没有对应卡片。

根因是**产物从来没有被建模**。它只是「某个副作用顺手打开的一个面板」。

## 命名：为什么叫 ChatArtifact 而不是 Artifact

`cli/ipc/artifacts.py` 里已经有 `Artifact` —— 那是**磁盘上的报告文件**（报告库、
`~/.wyckoff/reports`）。两者是不同的东西：

| | `Artifact`（已存在） | `ChatArtifact`（本协议） |
|---|---|---|
| 生命周期 | 持久化在磁盘 | 属于某一轮对话 |
| 寻址 | 相对路径 | `turnId:callId` |
| 来源 | 落盘的报告 | 工具执行结果 |

复用同一个名字会让「artifact」在代码里同时指两件事。前端类型叫 `ChatArtifact`，
事件类型叫 `chat_artifact`。

## 事件

`runtime.py` 已经发 `tool_result`（`event_type` 由变量拼出，grep 字面量会漏 ——
我第一次就是这么误判成「不存在」的）。它带 `name` / `args` / `result` /
`tool_call_id` / `status`。所以**不需要新增 runtime 事件类型**，只要在 IPC 层把
它翻译成产物。

翻译放在 IPC 层而不是 runtime，因为：

- runtime 是 CLI / TUI / 桌面共用的，「右侧面板」是桌面独有的概念。
- `_PASSTHROUGH` 已经是安全边界；产物投影天然属于这里。
- 工具结果里可能有凭据和内部结构，必须白名单挑字段，绝不能整个透传。

事件形状：

```json
{
  "type": "chat_artifact",
  "artifact_id": "turn-42:call_7",
  "kind": "kline",
  "title": "600519",
  "status": "ready",
  "payload": { "symbol": "600519", "timeframe": "1d" }
}
```

- `artifact_id` = `turnId:tool_call_id`。同一个工具调用重复投影时天然去重。
  **刻意不叫 `id`**：传输层会把 `event["id"]` 覆盖成请求流 id（stdio.py 的既有
  约定，审批事件当初也因此改用 `approval_id`）。叫 id 的话产物标识会被冲掉，
  前端就没法按它去重 —— 我写这层时就先踩了一次。
- `status`：`ready` | `failed`。**没有 `pending`** —— 见下面。
- `payload` 按 kind 白名单，不同 kind 各自挑字段。

## 为什么没有 pending 状态

审计建议卡片显示「生成中 / 已完成 / 失败」三态。但 `tool_start` 已经在对话流里
渲染成一行工具指示（`.tool` 块），再加一张「生成中」的产物卡片是同一件事说两遍。

而且「生成中」的卡片没有可点的东西 —— 它唯一的作用是占位。占位的代价是布局会
跳一次（卡片从生成中变成完成时高度变化）。

所以：**工具执行中沿用现有的 `.tool` 指示行，产物卡片只在 ready/failed 时出现。**
失败时也要出卡片，否则「工具跑了但没产物」看起来像什么都没发生。

## 自动展开策略

这是整套里唯一不能靠代码正确性保证的部分 —— 它是交互决策。规则：

1. **只有 `ready` 才自动展开。** 失败不开面板，只在对话里留失败卡片。
2. **每轮只自动展开第一个产物。** `annotate_chart` 一轮可被调用多次（每只票
   一次），现在每次都 `openKline`，连续三只票右侧跳三次。后续产物进页签，
   页签条上显示有新增。
3. **用户本轮关过面板，本轮不再自动弹。** 关闭是明确的「我不想看」信号。
4. **用户正在看别的产物时不切走。** 只在页签条上提示新增。
5. **窄窗口（< 1180px）不自动分栏。** 那个宽度下分栏会把会话挤成一条缝 ——
   与侧栏默认收起用的是同一个阈值。
6. **自动展开不移动键盘焦点。** 用 `aria-live="polite"` 宣告「600519 K 线已在
   右侧打开」，焦点留在输入框 —— 用户正在打字时抢焦点是最糟的。

第 2、3、4 条都是「不要打断用户」的不同侧面。共同点：**自动展开是便利，不是
命令**；一旦用户表达了自己的意图（关闭、切换、正在输入），便利就该让位。

## 分层

```
runtime.py            tool_result（已存在，不改）
    ↓
cli/ipc/session.py    _chat_artifact() 白名单翻译 → chat_artifact 事件
    ↓
lib/artifacts.ts      纯函数：事件 → ChatArtifact；按 id 去重
    ↓
lib/useArtifacts.ts   会话级注册表 + 自动展开决策（纯逻辑，可单测）
    ↓
shell.js              openArtifact(target) 收口 openKline / openReport
    ↓                 ├─ kind=kline   → 现有 Canvas
                      └─ kind=report  → 现有 markdown 渲染器
```

「渲染器」不是新东西：K 线继续用现有 Canvas，报告继续用现有 markdown。这一层
只是把两个入口收口成一个，让「打开哪个产物」变成数据而不是调用哪个函数。

**不引入画布库**（React Flow / tldraw / Konva）。右侧是个展示区，不是白板 ——
除非以后要做拖节点连线，那是另一个产品。

## 与旧路径的关系

`looksLikeReport()` 保留为兼容回退：老模型、或工具之外直接产出的长文本仍然靠它
识别。但它不再是主协议 —— 有 `chat_artifact` 事件时以事件为准，避免同一份报告
既被事件建模、又被文本猜测重复打开一次。

## 面板行为

**宽度按类型记。** K 线默认 52%、报告 46% —— 图要横向空间看趋势,报告是竖排文本,
共用一个宽度时看完图再看报告会觉得行太长。用户手动拖过之后按类型存起来,下次
打开同类沿用（手动拖动是明确偏好,不该被自动展开覆盖）。

**页签淘汰不动正在看的那个。** 超过 6 个仍会淘汰最老的,但候选里排除当前查看
的页签 —— 产物可以连着来,正在读的图被悄悄换掉是最费解的失败（用户没做任何
操作,内容就变了）。淘汰本身可以接受,因为对话里每个产物都有卡片,点得回来。

## 还没做的

- **报告仍靠 `looksLikeReport()` 识别**。它现在走注册表（因此享受同一套自动展开
  策略）,但「这段文本是不是报告」还是猜的。真正的解法是让产出报告的工具也发
  产物事件 —— 那要先有这样一个工具。
- **产物不跨会话持久化**。刷新窗口后注册表清空。要恢复得把产物写进对话历史,
  那是另一层（涉及 IPC 的会话恢复）。
- **只有 kline 一种工具产物**。表是白名单,加新的很直接,但每种都要定 payload
  该带什么。
